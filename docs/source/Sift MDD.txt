## 1.2 Assignment Interpretation and Mandatory Requirements
The original assignment mandates a transformational decision-support solution to bridge the gap between unstructured, multi-channel feedback collection and confident, defensible roadmap execution[cite: 1]. Seven mandatory operational requirements are derived directly from the core assignment parameters[cite: 1]:

1. **Multi-Source Feedback Ingestion:** Ingest and parse unstructured feedback originating from distinct touchpoints (support tickets, sales call transcripts, public reviews, in-app feedback)[cite: 1].
2. **Deep Theme Clustering:** Move beyond keyword tagging to group semantically equivalent feedback items under unified, cohesive thematic clusters[cite: 1].
3. **Root-Cause Identification:** Look beyond surface-level symptom reporting to formulate backing root-cause hypotheses grounded in technical or workflow failure conditions[cite: 1].
4. **Multivariable Prioritization:** Evaluate and score insights dynamically across Impact (revenue/tier weight), Frequency (volume), and Severity (operational blocker level)[cite: 1].
5. **Action-Oriented Recommendations:** Avoid passive summarization by generating explicit, role-tailored action recommendations (strategic rationales, engineering specifications, customer success mitigations)[cite: 1].
6. **Explainable Reasoning and Traceability:** Provide transparent mathematical scoring breakdowns and direct line-of-sight back to exact verbatim customer quotes[cite: 1].
7. **Noise, Bias, and Sample Size Safeguards:** Detect, filter, or down-weight non-actionable spam, emotional venting, duplicated entries, or statistically unrepresentative sample sizes to preserve decision quality[cite: 1].

## 1.3 Executive Overview of Sift
Sift is an AI-native product discovery and decision-support workspace designed for growth-stage B2B SaaS teams[cite: 1]. Sift ingests unstructured feedback exports (CSV/working tables)[cite: 1], separates non-actionable spam from emotional but actionable user feedback[cite: 1], semantically clusters recurring issues[cite: 1], formulates root-cause hypotheses[cite: 1], and calculates a dynamic, deterministic Hybrid Weighted Priority Score[cite: 1].

Rather than acting as a static dashboard or simple summarizer[cite: 1], Sift offers a dual-view discovery workspace combining a 2x2 Priority Matrix with a Color-Coded Card View[cite: 1], driven by interactive calibration sliders[cite: 1]. Every insight generated by Sift is traceable to source customer quotes via deterministic row-ID verification[cite: 1], exposes its mathematical formula[cite: 1], and produces copy-ready action outputs: Strategic Trade-off Rationales for Product Managers[cite: 1], Engineering Specs for Developers[cite: 1], and Workaround Advisory Drafts for Customer Success teams[cite: 1].

## 1.5 Core Problem Definition
Product organizations face a persistent "Data Overload vs. Decision Paralysis" challenge[cite: 1]. B2B SaaS companies collect hundreds of monthly customer comments across support tools, sales calls, app reviews, and surveys[cite: 1]. Converting this feedback into sprint priorities frequently fails due to three systemic breakdowns[cite: 1]:

1. **Loudest-Voice Bias:** Teams over-index on recent, angry, or highly vocal accounts while missing quiet, systemic issues that drive silent churn across the user base[cite: 1].
2. **Symptom vs. Root Cause Confusion:** Traditional tools group surface keywords (e.g., "Search is slow")[cite: 1], forcing teams to guess the underlying technical failure (e.g., "504 API Gateway Timeout on payloads >10,000 records")[cite: 1].
3. **The Trust Deficit (Black-Box AI):** Standard LLM tools generate broad bulleted summaries that teams cannot defend in sprint planning because they lack mathematical transparency, source quote receipts, or account-tier context[cite: 1].

# PART III — INTELLIGENCE, EVIDENCE AND DECISION QUALITY

## 3.1 AI vs. Deterministic Processing Responsibilities
To ensure accuracy and eliminate black-box unpredictability, Sift separates tasks between AI (LLM) and Deterministic code[cite: 1]:

* **AI / LLM Responsibilities (Configured with JSON schemas):**
  1. Semantic text parsing, emotion extraction, and problem isolation[cite: 1].
  2. Thematic cluster assignment and naming[cite: 1].
  3. Root-cause hypothesis formulation[cite: 1].
  4. Generating Strategic Trade-off Rationales, Engineering Specs (with `[NEEDS INVESTIGATION]` flags), and CS Advisory Drafts[cite: 1].
* **Deterministic Responsibilities (Client-Side JavaScript):**
  1. Exact Hybrid Priority Score calculations using normalized slider weights[cite: 1].
  2. Counting unique affected accounts ($U$) versus total incident volume ($N$)[cite: 1].
  3. String Verification Layer: Validating that quote snippets match source CSV row IDs verbatim[cite: 1].
  4. Workspace filtering, sorting, and user-interface updates[cite: 1].

## 3.2 Feedback Ingestion, Normalization, and Missing Metadata Policy
* **Text Normalization:** Standardizes character encoding, trims whitespace, and assigns a stable row identifier (`FB-001`, `FB-002`, ...)[cite: 1].
* **Customer Tier Mapping:** Maps entries to explicit buckets: `Enterprise` (Weight: 3.0), `Pro` (Weight: 2.0), `Free` (Weight: 1.0), and `UNKNOWN` (Weight: 1.0)[cite: 1].
* **Missing Metadata Policy:** Missing customer metadata (`ARR`, `Customer Tier`) must be strictly preserved as `UNKNOWN`[cite: 1]. `UNKNOWN` entries must not be implicitly assigned verified revenue or tier values, nor forced to `$0` or `Free`.

## 3.3 Deduplication and Theme Clustering Logic
* **Deduplication:** Distinguishes between **Total Incident Volume ($N$)** and **Unique Affected Accounts ($U$)**[cite: 1]. Multiple submissions from a single account increment incident volume ($N$) while preserving unique account count ($U = 1$) to prevent volume inflation[cite: 1].
* **Semantic Clustering:** Groups feedback items by underlying workflow problem rather than surface keywords[cite: 1]. LLM clustering is acknowledged as inherently non-deterministic across executions[cite: 1].

## 3.4 Impact, Frequency, and Severity Assessment
Every cluster $c$ is evaluated across three parameters[cite: 1]:
1. **Impact ($I_c$):** Revenue/Tier-weighted customer account value:
   $$I_c = \sum_{u \in U_c} \text{TierWeight}(u)$$
2. **Frequency ($F_c$):** Count of Unique Affected Accounts ($U_c$)[cite: 1].
3. **Severity ($S_c$):** Operational blocker level assigned on a 1–3 scale:
   * *Level 1 (Low):* Minor UX friction or cosmetic issue[cite: 1].
   * *Level 2 (Medium):* Workflow degraded, but a workaround exists[cite: 1].
   * *Level 3 (High):* Critical crash, data loss, or total workflow blocker[cite: 1].

## 3.5 Prioritization, Mathematical Scoring Specification and Comparability Policy
The Hybrid Priority Score ($P_c$) for cluster $c$ is calculated deterministically on a 0–100 scale using client-side JavaScript[cite: 1]:

### 1. Slider Weight Normalization
Given user slider values $w_{\text{ARR}}, w_{\text{Vol}}, w_{\text{Sev}} \in [0, 100]$:
$$W_{\text{ARR}} = \frac{w_{\text{ARR}}}{w_{\text{ARR}} + w_{\text{Vol}} + w_{\text{Sev}}}, \quad W_{\text{Vol}} = \frac{w_{\text{Vol}}}{w_{\text{ARR}} + w_{\text{Vol}} + w_{\text{Sev}}}, \quad W_{\text{Sev}} = \frac{w_{\text{Sev}}}{w_{\text{ARR}} + w_{\text{Vol}} + w_{\text{Sev}}}$$
*(Default weights: $w_{\text{ARR}} = 40, w_{\text{Vol}} = 40, w_{\text{Sev}} = 20$, yielding $W_{\text{ARR}} = 0.40, W_{\text{Vol}} = 0.40, W_{\text{Sev}} = 0.20$)*[cite: 1].

### 2. Dataset Component Normalization
$$I_n = \begin{cases} \frac{I_c}{\max_{k} I_k} & \text{if } \max_{k} I_k > 0 \\ 0 & \text{otherwise} \end{cases}$$
$$F_n = \begin{cases} \frac{U_c}{\max_{k} U_k} & \text{if } \max_{k} U_k > 0 \\ 0 & \text{otherwise} \end{cases}$$
$$S_n = \frac{S_c}{3.0}$$

### 3. Deterministic Priority Score Formula
$$P_c = 100 \times \left( W_{\text{ARR}} \cdot I_n + W_{\text{Vol}} \cdot F_n + W_{\text{Sev}} \cdot S_n \right)$$

* **Unified Global Comparability Policy:** Weights are never redistributed independently on a per-cluster basis[cite: 1]. All clusters across the dataset are scored using the exact same global scoring formula to preserve comparative integrity.

## 3.6 Root-Cause Hypotheses vs. Verified Facts
All AI-generated explanations are explicitly labeled **"Root-Cause Hypothesis"** in the UI[cite: 1]. The system displays a standard boundary notice:
> *"Root causes are AI-inferred hypotheses based on quote patterns. Verify against system logs before major engineering changes."*[cite: 1]

## 3.7 Evidence Traceability, Exact Quotation and Attribution Boundaries
* **Exact String Verification:** Quoted snippets in evidence panels must match exact substrings within the source record (`Feedback ID`)[cite: 1]. Non-exact matches or rewritten summaries are flagged as `Unverified`[cite: 1].
* **Attribution vs. Verification Boundary:** Verified quote receipts confirm source attribution (that a customer made a specific statement); they do not verify the technical accuracy of an AI root-cause hypothesis[cite: 1].

## 3.8 Confidence, Uncertainty, and Sample Size Safeguards
* **Critical Incident Safeguard:** Clusters with Level 3 Severity ($S_c = 3$) or high revenue impact ($I_c$) display a prominent **Critical Incident Flag**, ensuring severe issues are highlighted even if total volume ($F_c$) is low[cite: 1].
* **Small Sample Warning:** Clusters with fewer than 3 unique accounts display a **"Small Sample Size (Low Confidence)"** badge to prevent over-indexing on isolated requests[cite: 1].

## 3.9 Conflicting Feedback and Contradictory Evidence Handling
When a cluster contains opposing user requests, Sift generates a **Contradictory Evidence Notice** within the Strategic Trade-off Rationale[cite: 1], detailing:
* Percentage of users favoring Option A vs. Option B[cite: 1].
* Customer tier breakdown supporting each option (e.g., *"70% of Enterprise users prefer Option A, while 80% of Free users prefer Option B"*)[cite: 1].

## 3.10 Hallucination Prevention, Programmatic Validation, and Unsupported Claim Withholding
* **JSON Schema Enforcement:** LLM responses are validated against strict JSON schema structures[cite: 1].
* **Unsupported Claim Withholding:** AI summary claims or recommendations unsupported by source feedback records are flagged, redacted, or withheld from decision-ready outputs[cite: 1].
* **Spec Safety Placeholders:** Engineering specs for issues lacking explicit technical context automatically include `[NEEDS INVESTIGATION: Context Missing in Source Feedback]` placeholders[cite: 1].

## 3.11 Handling Insufficient, Noisy, Emotional, Manipulated, or Sensitive Data
* **Emotional Complaints:** Angry or emotional user feedback is parsed to extract the core functional complaint, preserving actionable signal without penalizing severity or discarding the entry[cite: 1].
* **Spam Filtering:** Non-actionable text (e.g., "asdfghjkl", "good app") is filtered into an Unclustered Bucket[cite: 1].

## 3.12 Explainability, Data Privacy, Transparency, and Human Review
Hovering over or clicking any Priority Score displays a **Formula Breakdown Tooltip** showing the exact component math[cite: 1]:

```

Score Formula Breakdown:

* Impact Component:     100 * 0.40 * (I_c / Max_I) = 32.0
* Frequency Component:  100 * 0.40 * (U_c / Max_U) = 28.0
* Severity Component:   100 * 0.20 * (S_c / 3.0)   = 13.3

---

Final Priority Score:                             = 73.3 / 100

```

## 4.2 Interactive 2x2 Matrix and Card Workspace Architecture
* **2x2 Priority Matrix (Left Pane):** Plots clusters on an Impact ($I_n$, $Y$-axis) vs. Frequency ($F_n$, $X$-axis) spatial grid[cite: 1]. Coordinates are determined strictly by underlying $I_n$ and $F_n$ metrics. Quadrants divide insights into *High Revenue Risk / High Volume*, *Enterprise Risk / Low Volume*, *Mass Friction / Low ARR*, and *Low Priority*.
* **Ranked Card Workspace (Right Pane):** Lists clusters sorted dynamically by Priority Score ($P_c$)[cite: 1]. Each card displays title, score badge, account count, total incident count, ARR risk sum, and action buttons[cite: 1].

## 4.3 Calibration Slider Behavior and Real-Time Interactive Updates
Moving any slider (ARR Weight, Volume Weight, Severity Weight) triggers a client-side recalculation of $P_c$ across all clusters[cite: 1]. The ranked card list re-sorts dynamically based on updated $P_c$ values[cite: 1]. Matrix plot coordinates ($I_n, F_n$) remain fixed unless underlying data metrics change.

## 4.6 Privacy, External Cloud AI Transmission, Key Security, and Ephemeral Memory Model
* **Browser Local Parsing:** CSV parsing, schema mapping, quote string verification, and priority score calculations run strictly browser-local in ephemeral client memory[cite: 1].

* **API Key Security & Proxy Model:** Private LLM API keys must **never** be embedded in browser-delivered JavaScript code. To maintain zero-additional-cost operation during evaluation, a free-tier serverless proxy function may be evaluated to forward requests to cloud AI providers without introducing persistent database requirements. Provider selection and backend architecture remain technical evaluation choices for the PRD stage.

Optimized for rapid development, utilizing native Web APIs, lightweight client-side frameworks, and secure API integration patterns.
